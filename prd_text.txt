1. Executive Summary
Sentinel is a production-grade, distributed API Security Gateway built on Spring Boot and Spring Cloud Gateway. It addresses a critical forensic gap in modern API security: when a cyberattack occurs, conventional gateways provide only a timestamp, status code, and IP address — wholly insufficient to reconstruct the mechanics of a breach, understand why a specific decision was made, or simulate what stricter policies might have prevented.
Sentinel closes this gap through three deeply integrated innovations:
Event Sourcing — every security decision is stored as an immutable, append-only event with full context (identity, policy rule fired, risk score, request fingerprint).
Zero-Trust ABAC Policy Engine — contextual Attribute-Based Access Control ensures no request is trusted by default; decisions combine JWT identity, endpoint, time-of-day, IP range, and behavioral risk score.
Forensic Replay Engine — a novel component that reconstructs the exact gateway state at any past timestamp and simulates alternative policy outcomes ("what-if" analysis).
This document is Version 2.0. It resolves all engineering gaps identified in the v1.0 review: locked dependency versions, append-only database enforcement DDL, SHA-256 event hash canonicalization, policy rule snapshot history, JWT key management, runtime policy refresh contract, data retention policy, demo fixture plan, and Prometheus metrics definitions.

8. Data Model & Schema
8.1 Events Table (Core Append-Only Store)
The events table is the heart of Sentinel. It is strictly append-only. A database-level trigger rejects any UPDATE or DELETE. The event_writer database role has INSERT-only privileges on this table. See Section 10.4 for the full DDL.
  NEW IN v2.0: policy_rule_snapshot_id column added to events table.
8.2 Policy Rules Table
8.3 Policy Rules History Table [NEW IN v2.0]
  NEW IN v2.0 — This table is essential for deterministic forensic replay.
This table stores a frozen immutable snapshot of every policy rule at the exact moment it was activated. Events in the events table reference this table via policy_rule_snapshot_id. The replay engine loads the snapshot from this table — never the current rule definition — ensuring that replays are deterministic regardless of subsequent rule changes.
Rows in this table are NEVER updated or deleted. When a rule is updated, the old snapshot row has deactivated_at set, and a new snapshot row is inserted. A trigger enforces this immutability.

10. Security Requirements
10.1 Authentication & Authorisation
All protected routes MUST require a valid, unexpired, correctly-signed JWT.
JWT signing algorithm SHALL be RS256 (asymmetric); HS256 is NOT permitted.
Role-based access to forensic and admin APIs SHALL be enforced at the Spring Security method level, not only at the gateway filter level.
Separate roles: GATEWAY_USER (pass-through), POLICY_ADMIN (rule management), FORENSICS_ADMIN (replay, export, simulation).
10.2 JWT Key Management & Rotation [NEW IN v2.0]
  NEW IN v2.0 — Answers how RS256 keys are provisioned, used, and rotated.
Key Provisioning:
Development / Demo: RS256 private key PEM file mounted into the gateway container at /run/secrets/sentinel_private_key.pem via Docker Compose volumes. The corresponding public key PEM is mounted at /run/secrets/sentinel_public_key.pem. Gateway reads key paths from environment variables SENTINEL_JWT_PRIVATE_KEY_PATH and SENTINEL_JWT_PUBLIC_KEY_PATH at startup.
CI Pipeline: Keys injected as base64-encoded environment variables SENTINEL_JWT_PRIVATE_KEY_B64 and SENTINEL_JWT_PUBLIC_KEY_B64. Gateway decodes and loads from environment on startup.
Keys are generated using RSA-2048 minimum. Example: openssl genrsa -out private_key.pem 2048 && openssl rsa -in private_key.pem -pubout -out public_key.pem
Key Rotation Procedure (Demo-testable):
Step 1: Generate new RSA key pair.
Step 2: Replace mounted key files (or update environment variables).
Step 3: Restart gateway container only (docker-compose restart gateway). No data loss; event store is unaffected.
Step 4: Issue new JWTs signed with the new private key. Old tokens signed with the old key will fail validation immediately.
Future (OIDC/JWKS path): The signing key location is abstracted behind a KeyProvider interface. A future JWKS endpoint implementation can be substituted without changing JWT validation logic.
Key security rules: Private key file MUST have chmod 400. Private key MUST NOT be committed to version control. .gitignore MUST include *.pem.
10.3 Event Hash Canonicalization — SHA-256 Specification [NEW IN v2.0]
  NEW IN v2.0 — Defines deterministic canonical serialization for tamper-evident hashing.
Without a deterministic canonical serialization, SHA-256 hash computation is non-reproducible across implementations. The following specification MUST be followed exactly.
Fields covered by event_hash (in this exact order):
event_id (UUID string, lowercase with hyphens, e.g., a3f1c2d4-e5b6-7890-abcd-ef1234567890)
timestamp_ns (decimal string representation of the BIGINT, e.g., "1707825840123456789")
event_type (string, e.g., "POLICY_DENIED")
session_id (UUID string, lowercase with hyphens)
user_id (string, or "null" if NULL)
endpoint (string)
http_method (string, uppercase)
decision (string, or "null" if NULL)
policy_rule_id (string, or "null" if NULL)
policy_rule_version (decimal string, or "null" if NULL)
risk_score (6 decimal place string, or "null" if NULL, e.g., "0.620000")
body_hash (hex string, or "null" if NULL)
gateway_version (string)
Canonical serialization algorithm:
1. For each field above, in the exact order listed:
     a. Convert to string using the rules above (NULL -> literal "null")
     b. Append field_name=field_value
     c. Append a single pipe | separator
2. Concatenate all field strings (no leading/trailing whitespace)
3. Encode the resulting string as UTF-8 bytes
4. Compute SHA-256 digest of the UTF-8 bytes
5. Encode digest as lowercase hexadecimal string (64 chars)
6. Store in event_hash column
Example canonical string (before hashing):
event_id=a3f1c2d4-e5b6-7890-abcd-ef1234567890|timestamp_ns=1707825840123456789|event_type=POLICY_DENIED|session_id=b1e2f3a4-c5d6-7890-1234-abcdef567890|user_id=user-9921|endpoint=/api/payments/delete|http_method=DELETE|decision=DENY|policy_rule_id=FIN-DELETE-BUSINESS-HOURS-01|policy_rule_version=1|risk_score=0.620000|body_hash=e3b0c44298fc1c149afb|gateway_version=1.0.0|
A HashVerificationUtil class SHALL be implemented that reads events from the store, recomputes the canonical hash, and reports any mismatch. This utility is invoked via GET /forensics/verify-hashes (see Section 9.1) and via CLI: java -jar sentinel-tools.jar verify-hashes --from 2025-01-01 --to 2025-12-31.
10.4 Append-Only Enforcement DDL [NEW IN v2.0]
  NEW IN v2.0 — Specifies the exact database mechanism enforcing immutability.
The following DDL SHALL be implemented as a Flyway migration (V1__create_events.sql and V2__append_only_trigger.sql):
-- events table trigger (Flyway: V2__append_only_trigger.sql)
CREATE OR REPLACE FUNCTION prevent_event_modification()
RETURNS TRIGGER AS $$
BEGIN
  RAISE EXCEPTION 'Events table is append-only. UPDATE and DELETE are forbidden.'),
  RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER events_append_only
BEFORE UPDATE OR DELETE ON events
FOR EACH ROW EXECUTE FUNCTION prevent_event_modification();

-- Dedicated write-only role
CREATE ROLE event_writer WITH LOGIN PASSWORD '${EVENT_WRITER_PASSWORD}';
GRANT INSERT ON events TO event_writer;
REVOKE UPDATE, DELETE ON events FROM event_writer;

-- Same pattern applied to policy_rules_history
CREATE TRIGGER policy_history_append_only
BEFORE UPDATE OR DELETE ON policy_rules_history
FOR EACH ROW EXECUTE FUNCTION prevent_event_modification();
The gateway application MUST connect to PostgreSQL using the event_writer role for all event and policy_rules_history writes. A separate read-only role (sentinel_reader) is used by the dashboard and forensics API.
Acceptance test: an integration test SHALL attempt a direct UPDATE on the events table using the event_writer role and verify that an exception is raised (AC-05).
10.5 Zero-Trust Enforcement
No request is implicitly trusted, even with a valid JWT. Every request is independently scored and policy-evaluated.
Policy default is DENY: if no rule matches, access is denied and POLICY_NO_MATCH event is emitted.
Contextual trust: time-of-day, source IP, and risk score are evaluated on every request, not just at session initiation.
10.6 Data Protection
Request bodies MUST NOT be stored in plaintext. Only SHA-256 hash stored.
Configurable field-level PII redaction: fields listed in application config are replaced with [REDACTED] before event persistence.
JWT signing keys and database credentials SHALL be injected via environment variables or mounted secret files; no secrets in source code.
Event store access is restricted to internal Docker network; no direct PostgreSQL port exposed to host.

C. Tamper Verification Runbook [NEW IN v2.0]
  NEW IN v2.0 — Step-by-step guide for demonstrating tamper evidence at viva.
Steps to demonstrate tamper detection during viva:
Step 1: Load demo fixtures. Run: bash fixtures/load_demo_sessions.sh
Step 2: Verify all events are clean. Call GET /forensics/verify-hashes?from_ns=0&to_ns=9999999999999999999. Expected response: { "tampered_count": 0, "checked": N }
Step 3: Manually tamper one event. Run SQL directly: UPDATE events SET decision = 'ALLOW' WHERE event_id = '<known_event_id_from_F03>';
Step 4: Re-run tamper verification. Call GET /forensics/verify-hashes again. Expected response: { "tampered_count": 1, "tampered_events": ["<event_id>"] }
Step 5: Interpret. The system detected that decision='ALLOW' does not match the stored event_hash (which was computed when decision='DENY'). This proves the audit trail is cryptographically verifiable.
CLI alternative: java -jar sentinel-tools.jar verify-hashes --from 2025-01-01 --to 2025-12-31 --db-url jdbc:postgresql://localhost:5432/sentinel

F. Demo Script — Viva End-to-End Flow
The following sequence constitutes the full demo for viva examination:
Start the full stack: docker-compose up. All services healthy in < 5 minutes.
Load demo fixtures: bash fixtures/load_demo_sessions.sh. Confirm 3 sessions loaded.
Send a valid request to /api/users/profile with correct JWT → HTTP 200. Show REQUEST_RECEIVED + POLICY_ALLOWED events in the event store.
Send same request with an expired JWT → HTTP 401. Show AUTH_FAILED event with failure reason.
Send DELETE to /api/payments/delete outside business hours → HTTP 403. Show POLICY_DENIED event with exact rule_id FIN-DELETE-BUSINESS-HOURS-01 and policy_rule_snapshot_id.
Show pre-loaded attack session F-03 in Forensic Dashboard → Filter by session_id → Full 10-event attack timeline in order.
Click Policy Decision Trace on the POLICY_DENIED event → Show rule conditions, frozen snapshot used, which condition caused denial.
Launch What-If Simulation: take the attack session (F-03), modify the time-range rule to block all hours → Run simulation → Show first_divergence_step moves earlier.
Show Alert List → High-risk attack session F-03 at top. Show Prometheus metrics panel — all 5 metrics visible.
Demonstrate tamper detection (Appendix C runbook): tamper one event → run /forensics/verify-hashes → mismatch detected.
Run load test (200 RPS, 60 seconds) → Show p99 latency ≤ 15ms from benchmark output.
